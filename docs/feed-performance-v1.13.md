# 피드 성능 측정 기록 (v1.13)

v1.13.0(RSS 예약 수집과 DB 저장)과 v1.13.1(Vercel 함수 서울 지정) 전후로 피드 첫 로드가 얼마나 달라졌는지 측정한 기록입니다.
다음에 같은 방식으로 다시 재서 비교할 수 있게 조건과 방법을 함께 남깁니다.

- 측정일: 2026-10-14
- 비교 버전: v1.12.1(요청 때 RSS 수집, 15분 서버 캐시) / v1.13.0 / v1.13.1(최신)
- 대상 화면: 피드 테크 블로그 탭 `/feeds?category=tech_blog`, 피드 API `/api/feeds?category=tech_blog&limit=12`

- **재방문은 이전이 조금 빨랐습니다.** 이전에는 서버 메모리 캐시에서 바로 줬고, 지금은 매번 DB를 조회합니다. 차이는 0.05~0.2초입니다.
- 이전 버전의 긴 대기는 서버 캐시가 비었을 때, 주로 배포 직후에 생겼습니다. 캐시가 만료돼도 지난 결과를 먼저 주고 뒤에서 새로 받았기 때문에 대부분의 방문자는 겪지 않았습니다.
- **LCP는 두 버전이 같습니다.** LCP 요소가 첫 카드의 외부 썸네일이고, JS 실행 뒤 브라우저가 피드를 다시 요청해야 그려지기 때문입니다(아래 "남은 개선점").

## 측정 조건

### 로컬 비교

두 버전의 production 빌드를 같은 맥에서 띄우고 같은 운영 Supabase(서울)에 연결했습니다. 이전 Production 배포는 Vercel 로그인으로 보호돼 직접 잴 수 없어 이 방식을 썼습니다.

- 장비: Apple M3 Pro, Node.js 26, Chrome headless
- 빌드: 각 태그를 `git worktree`로 꺼내 `next build` 후 `next start`
- 환경 변수: 운영 Supabase URL과 공개 anon 키
- 서버 캐시 없음(첫 방문): 서버를 다시 시작하고 `.next/cache/fetch-cache`를 지운 뒤 첫 요청
- 서버 캐시 있음(재방문): 같은 서버에 요청을 한 번 보낸 뒤 측정
- 브라우저 캐시: 매 측정마다 비움

### Production

- v1.13.0: Vercel 함수 지역 워싱턴(iad1), 응답 헤더 `x-vercel-id: icn1::iad1`
- v1.13.1: Vercel 함수 지역 서울(icn1), 응답 헤더 `x-vercel-id: icn1::icn1`
- 측정 위치: 서울

## 측정의 한계

- 이전 버전의 Production 환경은 재지 못했습니다. 당시 함수는 미국 워싱턴에서 한국 블로그 RSS를 가져왔으므로 Production 첫 방문은 로컬 수치(2.6~4.6초)보다 더 느렸을 가능성이 큽니다. 확인한 수치는 아닙니다.
- 로컬 측정은 맥과 Supabase가 모두 서울에 있어 DB 왕복이 짧습니다.
- Lighthouse 모바일 값은 느린 환경을 흉내 낸 추정치라 실제 휴대폰보다 보수적입니다.
- 측정 횟수가 3~13회라 편차가 큰 항목(Production 첫 요청 등)은 범위로 적었습니다.

## 남은 개선점

- **모바일 LCP.** LCP 요소는 첫 카드의 외부 썸네일입니다. 순서가 "페이지 수신 → JS 실행 → 브라우저가 `/api/feeds` 요청 → 카드 렌더 → 썸네일 요청"이라 렌더 지연이 LCP의 대부분입니다(Production 모바일에서 5.2초 중 약 3.1초). 서버에서 첫 페이지 카드를 미리 그려 보내면 이 지연이 줄어듭니다.
- **데스크톱 LCP 이미지의 지연 로딩.** 데스크톱에서는 LCP 썸네일에 `loading="lazy"`가 붙어 있습니다. 첫 줄 카드 이미지는 우선 로딩 대상에 넣는 것을 검토합니다(`shouldPrioritizeImage`).

## 다시 측정하는 방법

1. 비교할 두 태그를 `git worktree add <경로> <태그>`로 꺼내고 `node_modules`를 복사한 뒤 `next build`합니다. 환경 변수는 운영 Supabase URL과 공개 anon 키를 씁니다.
2. 각각 `next start -p <포트>`로 띄웁니다. 서버 캐시 없는 상태는 서버를 다시 시작하고 `.next/cache/fetch-cache`를 지운 뒤 측정합니다.
3. API: `curl -o /dev/null -w "%{time_total}" "localhost:<포트>/api/feeds?category=tech_blog&limit=12"`
4. Lighthouse: `npx lighthouse@12.8.2 "http://localhost:<포트>/feeds?category=tech_blog" --only-categories=performance [--preset=desktop] --chrome-flags="--headless=new" --output=json`
5. Production 함수 지역은 응답 헤더 `x-vercel-id`의 두 번째 값으로 확인합니다.
