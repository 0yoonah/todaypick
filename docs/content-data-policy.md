# 콘텐츠 데이터 관리 기준

퀴즈, CS 지식 질문, IT 용어 같은 **콘텐츠를 코드와 DB 중 어디에 둘지** 판단하는 기준입니다.
새 콘텐츠를 추가하거나 기존 데이터를 옮길지 검토할 때 이 문서를 먼저 확인합니다.

## 현재 구조

경계는 **"모든 사용자에게 같은 값인가"** 입니다.

| 구분 | 저장 위치 | 예 |
| --- | --- | --- |
| 콘텐츠 | 코드 (`src/data/*.ts`) | 퀴즈 40문항, CS 지식 80문항, IT 용어 121개, RSS 소스 목록, 명언 |
| 사용자별 기록 | DB (Supabase) | 채점 결과, 읽은 글, 일일 활동, 스크랩, 작성한 글, 북마크 |

모든 사용자에게 같은 값이면 코드, 사용자마다 다른 값이면 DB입니다.

## 코드로 관리하는 이유

**정합성을 테스트로 고정할 수 있습니다.**
`src/data/*.test.ts`가 중복 id, 잘못된 참조, 범위를 벗어난 값 등을 CI에서 잡습니다.
실제로 이 테스트가 중복 별칭, 배열의 이중 콤마로 생긴 `undefined` 원소, 존재하지 않는 관련 용어 id를 잡아냈습니다.
DB였다면 제약 조건을 따로 걸거나 런타임에 드러났을 문제입니다.

**서버 렌더링에 유리합니다.**
조회 없이 초기 HTML에 콘텐츠를 담을 수 있어 검색 노출과 첫 화면 표시에 유리합니다.
DB로 옮기면 조회 지연과 캐시 전략을 함께 설계해야 합니다.

**변경 이력이 PR에 남습니다.**
문항을 왜 바꿨는지 리뷰와 커밋 이력으로 추적되고 되돌리기 쉽습니다.

**운영 비용이 없습니다.**
쿼리도, 장애 지점도, 관리 화면도 필요하지 않습니다.

## DB로 옮겨야 하는 신호

아래 중 **하나라도 해당되면** 전환을 검토합니다.

1. **개발자가 아닌 사람이 콘텐츠를 편집**해야 한다.
   관리 화면이 필요해지고, 그러면 DB가 전제가 됩니다.
2. **사용자 제보나 기여**를 받는다.
   사용자가 만든 데이터는 처음부터 DB에 둡니다.
3. **항목이 수백 개를 넘어** 파일 관리가 버겁다.
   기준점은 한 종류당 약 300개입니다. 그 이상이면 파일 분할이나 DB 이전을 검토합니다.
4. **배포 없이 즉시 고쳐야 하는** 콘텐츠 오류가 잦다.
   오탈자 하나에 배포가 필요한 상황이 반복되면 비용이 역전됩니다.

전환할 때는 다음을 함께 준비합니다.

- 관리 화면 또는 데이터 반입 절차
- 조회 캐시 전략과 서버 렌더링 유지 방안
- 코드에서 테스트로 잡던 정합성을 대신할 DB 제약 조건
- 기존 id를 보존하는 이전 계획. 사용자 기록이 id를 참조하고 있으면 끊기면 안 됩니다

## 코드로 관리할 때 지킬 것

- **`created_at` 같은 값은 고정 상수로 둔다.** `new Date()`를 쓰면 모듈이 로드될 때마다 값이 달라집니다.
- **정합성 테스트를 함께 작성한다.** 최소한 id 중복, 필수 값 존재, 참조 유효성, 분류 범위를 확인합니다.
- **id를 함부로 바꾸지 않는다.** 사용자 기록이 id로 콘텐츠를 참조합니다. 분류나 문구가 바뀌어도 id는 유지합니다.
- **클라이언트 번들에 싣지 않는다.**
  콘텐츠 목록은 서버 컴포넌트에서 렌더링하고, 클라이언트 컴포넌트에는 화면에 필요한 값만 넘깁니다.
  클라이언트 컴포넌트가 `src/data`를 직접 import하면 데이터 전체가 번들에 포함됩니다.
- **분류 체계를 재사용한다.** 서로 연결될 콘텐츠는 같은 분류 타입을 공유해 기준이 갈라지지 않게 합니다.
