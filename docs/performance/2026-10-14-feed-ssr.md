# 피드 첫 페이지 서버 렌더링 (v1.13.1 → v1.13.2)

v1.13.2에서 피드 화면의 표시 속도(LCP)를 개선한 뒤 Production에서 측정한 기록입니다. 측정 방법은 [README](README.md)를 따릅니다.

- 측정일: 2026-10-14, 서울에서 측정
- 비교 대상
  - 이전: v1.13.1 Production. 카드는 브라우저가 `/api/feeds`를 요청한 뒤 그려지고, 첫 카드 외 이미지는 지연 로딩, 이미지는 받기 전까지 투명
  - 현재: v1.13.2 Production. 첫 페이지 카드를 서버에서 그려 HTML과 함께 보내고, 첫 줄(앞 3장) 이미지는 지연 로딩하지 않으며, 첫 화면 이미지는 처음부터 보임
- 대상: 피드 테크 블로그 탭 `/feeds?category=tech_blog`
- v1.13.1 값은 같은 날 [DB 저장 측정](2026-10-14-feed-db-collection.md)에서 잰 Production 수치입니다.

## 결과

v1.13.2에서 피드 화면의 첫 페이지 카드를 서버에서 미리 그려 HTML과 함께 보내고, 첫 줄(앞 3장) 썸네일을 지연 로딩하지 않으며, 첫 화면 이미지를 받기 전에 투명하게 숨기지 않도록 바꿨습니다. 같은 날 v1.13.1과 같은 방법으로 쟀습니다.

| Lighthouse (3회 중앙값) | v1.13.1 | v1.13.2 |
| --- | --- | --- |
| 모바일 점수 | 76 | 88 |
| 모바일 LCP | 7.6초 | 3.9초 |
| 모바일 Speed Index | 1.10초 | 1.14초 |
| 데스크톱 점수 | 90 | 97 |
| 데스크톱 LCP | 2.1초 | 1.3초 |
| 데스크톱 Speed Index | 0.50초 | 0.44초 |

- 모바일 각 회차: 점수 79·90·88, LCP 5.7·3.6·3.9초. 첫 회는 함수가 쉬고 있던 상태로 보입니다.
- 데스크톱 각 회차: 점수 99·97·95, LCP 0.78·1.28·1.54초
- **LCP가 모바일 절반, 데스크톱 60% 수준으로 줄었습니다.** 카드가 HTML에 들어 있어 브라우저의 피드 요청을 기다리지 않고, 첫 화면 이미지가 처음부터 보이는 상태라 이미지를 받는 즉시 LCP가 기록됩니다.
- 페이지 첫 바이트(TTFB)는 서버 조회만큼 늘었습니다. `/feeds` 0.21초(3회).
- 첫 카드가 DOM에 나타나는 시간(8회)은 0.24~1.88초, 중앙값 0.59초로 v1.13.1(0.42초)보다 편차가 컸습니다. 카드가 HTML 파싱과 함께 나타나므로 TTFB와 HTML 크기의 영향을 받습니다. 사용자가 보는 화면 기준인 LCP로 판단합니다.

## 측정 조건

- Lighthouse 12.8.2, 성능 카테고리만. 모바일은 기본 설정(느린 4G와 CPU 감속을 흉내 낸 값), 데스크톱은 `--preset=desktop`. 각 3회의 중앙값
- 첫 카드 DOM 시간과 TTFB는 브라우저 캐시를 비운 Chrome headless(데스크톱 1280px), 비로그인 상태

## 측정의 한계

- Lighthouse 모바일 LCP는 외부 이미지 응답에 따라 편차가 큽니다(같은 날 v1.13.1 1회 측정에서 5.2초가 나온 적도 있음).
- 실제 방문자 기준 지표는 아직 없습니다.

## 남은 개선점

- **외부 썸네일 크기.** 모바일 LCP 3.9초의 남은 부분은 출처 서버의 원본 이미지를 그대로 받는 시간입니다. 출처 정책상 Vercel 이미지 최적화로 복제하지 않으므로, 개선하려면 RSS가 주는 작은 크기 이미지를 고르는 방법을 검토합니다.
- **실사용자 지표.** Vercel Speed Insights로 실제 방문자의 LCP를 모으면 실험실 측정과 함께 볼 수 있습니다.
- 모바일에서는 화면 밖인 2~3장 이미지도 지연 로딩하지 않습니다.
