# 피드 DB 저장과 함수 지역 변경 (v1.12.1 → v1.13.1)

v1.13.0(RSS 예약 수집과 DB 저장)과 v1.13.1(Vercel 함수 서울 지정)로 피드 첫 로드가 얼마나 달라졌는지 측정한 기록입니다. 측정 방법은 [README](README.md)를 따릅니다.

- 측정일: 2026-10-14, 서울에서 측정
- 비교 대상
  - 이전: v1.12.1 Production 배포. 요청 때 RSS 수집, 15분 서버 캐시, 함수 지역 워싱턴(iad1). 배포 당시 커밋은 `d1da3fc`입니다. 같은 날 커밋 작성자를 정리하면서 v1.12.1 태그는 다른 커밋 번호를 가리키지만 내용은 같습니다.
  - 현재: v1.13.1 Production. DB에서 읽기, 함수 지역 서울(icn1)
- 대상: 피드 테크 블로그 탭 `/feeds?category=tech_blog`, 피드 API `/api/feeds?category=tech_blog&limit=12`

## 요약 (Production)

| 항목 | v1.12.1 | v1.13.1 |
| --- | --- | --- |
| 피드 API, 서버 캐시가 만료된 뒤 첫 요청 | **7.8초** (테크 블로그), 1.2초 (IT 뉴스) | 해당 없음 (항상 DB 조회) |
| 피드 API, 캐시가 살아 있을 때 (10회 중앙값) | 0.41초 (테크 블로그), 0.35초 (IT 뉴스) | 0.21초 (두 탭 모두) |
| 첫 카드가 보일 때까지 (8회 중앙값) | 0.56초 | 0.42초 |
| Lighthouse 모바일 Speed Index (3회 중앙값) | 1.39초 | 1.10초 |
| Lighthouse 데스크톱 Speed Index (3회 중앙값) | 0.57초 | 0.50초 |
| Lighthouse 점수 / LCP | 모바일 76 / 7.7초, 데스크톱 90 / 2.0초 | 모바일 76 / 7.6초, 데스크톱 90 / 2.1초 |

- **가장 큰 차이는 캐시가 만료된 뒤의 첫 방문입니다.** 이전 버전은 마지막 요청 뒤 15분이 지나면, 다음 방문자가 테크 블로그 출처 29곳을 워싱턴에서 모두 받을 때까지 **7.8초**를 기다렸습니다. 방문이 드문 시간대에는 대부분의 방문자가 이 경우에 해당합니다. 현재는 언제 열어도 약 0.2초입니다.
- **캐시가 살아 있을 때도 빨라졌습니다.** API 0.41초 → 0.21초, 첫 카드 0.56초 → 0.42초. 함수가 DB와 같은 서울에서 실행되기 때문입니다.
- **Lighthouse 점수와 LCP는 그대로입니다.** LCP 요소가 첫 카드의 외부 썸네일이고, JS 실행 뒤 브라우저가 피드를 다시 요청해야 그려지기 때문입니다([첫 페이지 서버 렌더링 측정](2026-10-14-feed-ssr.md)에서 개선).

## 측정 조건

- 이전 배포는 고유 주소(`todaypick-2cklidu3c-0yoonah.vercel.app`)로 접근했습니다. 측정하는 동안 Vercel Deployment Protection(Vercel Authentication)을 잠시 끄고, 끝난 뒤 다시 켰습니다.
- 두 배포 모두 같은 운영 Supabase(서울)를 씁니다. 이전 배포는 `feed_items`를 쓰지 않고 RSS를 직접 수집합니다.
- 함수 실행 지역은 응답 헤더 `x-vercel-id`로 확인했습니다. 이전 `icn1::iad1`, 현재 `icn1::icn1`
- 브라우저 측정은 매번 브라우저 캐시를 비운 Chrome headless(데스크톱 1280px)입니다.
- 비로그인 상태입니다. 로그인하면 스크랩 상태 조회가 더해집니다.

## 결과

### 피드 API 응답 시간

`curl`로 같은 요청을 연속 10회 보냈습니다. 이전 버전은 `page=1`을 붙였습니다.

| | v1.12.1 (워싱턴) | v1.13.1 (서울) |
| --- | --- | --- |
| 테크 블로그 | 0.35~1.08초, 중앙값 0.41초 | 0.19~0.43초, 중앙값 0.21초 |
| IT 뉴스 | 0.33~1.21초, 중앙값 0.35초 | 0.18~0.33초, 중앙값 0.21초 |

이전 버전에서 마지막 요청 뒤 16분을 기다렸다가 다시 요청했습니다.

| | 만료 뒤 첫 요청 | 8초 뒤 다음 요청 |
| --- | --- | --- |
| 테크 블로그 | **7.82초** | 0.56초 |
| IT 뉴스 | 1.15초 | 0.40초 |

캐시가 만료되면 그 요청이 RSS 수집이 끝날 때까지 기다렸습니다. 출처가 많은 테크 블로그에서 대기가 깁니다.

### 함수 지역 변경 (v1.13.0 → v1.13.1)

같은 코드에서 Vercel 함수 지역만 바꿨습니다(각 6~8회).

| | v1.13.0 (워싱턴 iad1) | v1.13.1 (서울 icn1) |
| --- | --- | --- |
| 테크 블로그 | 0.56~1.10초 | 0.19~0.49초 (대부분 0.2초 안팎) |
| IT 뉴스 | 0.56~1.02초 | 0.19~0.39초 (대부분 0.2초) |

함수가 미국에 있으면 요청마다 서울 DB까지 2~3번(로그인 확인, 피드 조회, 로그인 시 스크랩 상태) 태평양을 왕복합니다. 함수 지역은 `vercel.json`의 `regions`로 고정했습니다.

### 첫 카드가 보일 때까지

화면을 열고 첫 피드 카드(원문 링크)가 DOM에 나타난 시점의 `performance.now()`입니다. 8회.

| | 측정값 | 중앙값 |
| --- | --- | --- |
| v1.12.1 | 1.06, 0.69, 0.55, 0.57, 0.56, 0.55, 0.54, 0.56초 | 0.56초 |
| v1.13.1 | 0.43, 0.49, 0.39, 0.37, 0.36, 0.48, 0.42, 0.44초 | 0.42초 |

이 측정은 직전 API 측정으로 이전 버전의 캐시가 살아 있는 상태에서 했습니다. 캐시가 만료된 상태였다면 이전 버전은 위 API 결과만큼(약 7.8초) 더 기다립니다.

Lighthouse 12.8.2, 성능 카테고리만. 모바일은 기본 설정(느린 4G와 CPU 감속을 흉내 낸 값), 데스크톱은 `--preset=desktop`. 각 3회의 중앙값입니다.

| --- | --- | --- | --- | --- | --- | --- |
| 모바일 v1.12.1 | 76 | 1.14초 | 7.7초 | 0ms | 0.028 | 1.39초 |
| 모바일 v1.13.1 | 76 | 1.10초 | 7.6초 | 0ms | 0.028 | 1.10초 |
| 데스크톱 v1.12.1 | 90 | 0.37초 | 2.0초 | 0ms | 0.021 | 0.57초 |

- Lighthouse 측정도 이전 버전의 캐시가 살아 있는 상태입니다.

## 측정의 한계

- 측정 횟수가 3~10회라 편차가 큰 항목은 범위와 중앙값을 함께 적었습니다.
- 캐시 만료 뒤 첫 요청은 카테고리마다 1회입니다. 출처 응답 속도에 따라 달라집니다.
- Lighthouse 모바일 값은 느린 환경을 흉내 낸 추정치라 실제 휴대폰보다 보수적입니다.
- 실제 방문자 기준 지표는 아직 없습니다. Vercel Speed Insights를 켜면 실제 방문자 브라우저에서 LCP 등을 모을 수 있습니다.
